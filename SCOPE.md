# Scope

What this repository contains, what it deliberately does not, and why.

---

## The short version

This is a **read-side** curriculum. It teaches you to recognize, analyze, detect, and recover from ransomware encryption. It does not teach you to build an encryptor, and it contains no code that would meaningfully help someone do so.

That is a design decision, not an oversight or a legal hedge.

---

## Why the line is drawn here

**An incident responder never needs to author an encryptor.** The skills that are actually scarce, and actually billable, are the read-side ones: identifying a cipher in a stripped Go binary, recovering an AES key from a memory image, reading an entropy profile correctly, telling a client which of their files are recoverable and defending that answer. None of those require the ability to write ransomware.

**The write-side skills transfer directly to harm; the read-side ones do not.** A working hybrid encryptor is a working hybrid encryptor regardless of the folder it sits in or the disclaimer above it. A footer parser is not.

**The cryptography itself is not the sensitive part.** Hybrid encryption is textbook material — it is how TLS and PGP work, and this repository explains it in full. What we omit is the *assembled, operational* version: target selection, anti-recovery, throughput optimization, and evasion, which are the parts that turn a cryptography exercise into a weapon.

---

## Specifically not included

| Omitted | Why |
|---|---|
| Encryptor proof-of-concept (ephemeral key → asymmetric wrap → footer append → key wipe) | This is the ransomware core. Everything else is delivery |
| File traversal with OS-path and extension exclusions | Target selection logic |
| Shadow copy / backup destruction implementations | Anti-recovery. This is what makes an incident unrecoverable |
| Restart Manager handle-release to reach locked database files | Exists specifically to encrypt files that are in use |
| Intermittent encryption tuned against I/O rate monitoring | Evasion |
| Threading and IOCP designs for parallel encryption throughput | Speed is the attacker's primary constraint. We do not help with it |
| BYOVD or kernel-mode encryption | Evasion and privilege abuse |
| Working exploit code for any CVE referenced in a case study | Out of scope entirely |

Case studies **describe** these behaviors at the level published threat intelligence does, because you cannot detect what you cannot describe. They do not provide implementations.

---

## Specifically included

- Cryptographic theory in full, including the hybrid model and per-file ephemeral ECDH
- Algorithm identification: constants, API surfaces, container magics
- Windows crypto API mechanics as a **recognition** skill
- Memory forensics and key recovery — the victim's side of the same coin
- Detection content: YARA, Sigma logic, behavioral analytics, hunting guidance
- Triage and analysis tooling that reads and reports, never writes or destroys
- Decryption and recovery tooling
- Case studies grounded in primary sources
- Safe synthetic specimen generation, so nobody needs live malware to practise

### The demo tool, and why it is not an encryptor

[`01-Symmetric-Cryptography/labs/encryption_demo.py`](01-Symmetric-Cryptography/labs/encryption_demo.py) performs real AES. It is a teaching tool, not a weapon, because of four properties enforced in the code and asserted in [`tests/`](tests/):

1. The key is **fixed, hardcoded, and printed on every run**. Nothing is ephemeral or secret.
2. There are **no asymmetric operations at all**. No RSA, no ECC, no key wrapping.
3. The key is **never destroyed**, and decryption is included and demonstrated.
4. Originals are **never overwritten, renamed, or deleted**. Output is always a new file.

Ransomware is defined by irreversibility for the victim: a random key they never see, wrapped under a public key whose private half they will never have, then wiped from memory. Remove those and what remains is a cryptography tutorial where every step is reversible by design.

## Contribution policy

Pull requests adding any item from the omitted list will be closed without merge, however they are framed. Educational intent does not change what the code does once it is public.

Wanted: detection content, analysis and recovery tooling, case studies grounded in primary sources, corrections, and improved explanations. See [CONTRIBUTING.md](CONTRIBUTING.md).

---

## Live samples

Several modules reference real malware. This repository **hosts no samples and no sample links.** [`labs/SAMPLE_SOURCING.md`](labs/SAMPLE_SOURCING.md) covers obtaining them legitimately, and [`labs/SAFE_LAB_SETUP.md`](labs/SAFE_LAB_SETUP.md) is mandatory reading before you handle any.

Every lab in this repository can be completed with **synthetic specimens** generated by the demo tooling. Live samples are optional throughout.

---

## If you think the line is drawn wrongly

Open an issue. The reasoning above is a position, not a decree, and a well-argued case that some specific omission is both necessary for defense and not meaningfully uplifting to an attacker will be read seriously. "It's for education" on its own is not that argument, because it is equally available to anyone.
